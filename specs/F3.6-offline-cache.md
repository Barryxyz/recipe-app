# F3.6 Offline cache & sync

**Phase** 3 · **Size** L · **Prototype** no · **Requirements** NFR-6 · **Depends on** F0.3 (schema additions), most of Phase 1–3

## Summary
A SwiftData mirror of the user's data. Pantry, recipes and the shopping list can be viewed and edited offline, including manual entry, and changes sync when back online. The server stays the source of truth.

## Cached locally
| Data | Direction |
|---|---|
| `pantry_items`, `shopping_list_items`, `recipes` + `recipe_ingredients`, `user_prefs`, `user_shelf_life_overrides`, `ingredients_private` | Both ways |
| Catalog subset: every ingredient the user has used, plus the most common ~500 items with shelf life and units | Pull only, refreshed weekly |

The catalog subset lets manual entry (F1.5) search and calculate expiry offline. Offline search is a prefix and substring match on the local subset.

## Schema support (in DESIGN §5 and F0.3)
- `updated_at timestamptz` with a trigger on all synced tables, plus `deleted_at` on tables where rows get deleted.
- **Deletes become soft deletes** (`deleted_at` set) so other devices learn about them. A nightly job purges rows deleted more than 30 days ago.
- The 50-recipe trigger and queries must ignore soft-deleted rows.
- `recipe_ingredients` sync with their recipe: when a recipe's `updated_at` changes, its ingredient rows are pulled again.

## Sync design
- **IDs** are client-generated UUIDs, so offline creates need no ID remapping.
- **Pull:**
  - When: on launch, on foreground, on pull-to-refresh, and every 5 min while open.
  - What: for each table, `select * where updated_at > last_pulled_at` (including soft-deleted rows), applied to SwiftData.
  - `last_pulled_at` comes from the server's clock (returned by an RPC), not the device's.
- **Push:** every local change goes into an **outbox** (table, id, operation, payload, created_at). The outbox is sent in order when online. Each operation is idempotent: upsert by id, or set `deleted_at`.
- **Conflicts:** last write wins per row, by server `updated_at`. In a single-user household this is rare, and it's acceptable.
- **Server-only steps:** expiry calculation (F1.6) and macro calculation (F2.3) run on the server after push. The client shows its local preview until the pull brings the server values.
- **Not available offline:** scan, generate, share and recompute macros. Those buttons are disabled and labeled "Needs internet".

## UI
- A small cloud icon with a count shows pending changes.
- An "Offline" banner shows when there's no connection.

## Acceptance criteria
- [ ] In airplane mode: the pantry, recipes and shopping list are viewable. Items can be added manually with an expiry date, edited, and marked used.
- [ ] After reconnecting, every offline change reaches the server within 10 s, with no duplicates.
- [ ] A delete on one device disappears on another after a pull.
- [ ] Killing the app with a pending outbox keeps it, and it syncs on the next launch.
- [ ] Sign out and delete account wipe the local store.
