# F0.6 Purchase verification

**Phase** 0 · **Size** S · **Prototype** no (`REQUIRE_PURCHASE=false`) · **Requirements** NFR-8, D5 · **Depends on** F0.2, F0.3, F0.5

## Summary
The app is a $4.99 paid download. The Supabase anon key ships inside the app and is public, so without a check anyone could create an anonymous account with a script and call the AI functions for free. Before allowing AI calls, the server checks Apple-signed proof that the account belongs to someone who bought the app.

## Flow
1. **When the app sends proof:** after sign-in on first launch, after signing in with Apple on a new device, and on any launch where the account isn't yet verified. The app gets `AppTransaction.shared` (StoreKit 2) and sends its `jwsRepresentation` to `POST /verify-purchase`.
2. **The function checks the proof:**
   - The JWS signature chain is valid against Apple's root certificates. Use Apple's App Store Server Library rather than hand-rolled checks.
   - `bundleId` matches the app.
   - `environment` is `Production` or `Sandbox`. Sandbox proof only comes from builds Apple distributes (TestFlight and **App Review**), so prod must accept it, or reviewers couldn't use the AI features and would reject the app.
   - `Xcode` proof (local StoreKit testing) is accepted only when `ALLOW_XCODE=true` (dev only).
3. **On success:** set `app.users.purchase_verified_at = now()` and `purchase_environment`. Only the service role can write these columns (F0.3), so a client can't mark itself verified.
4. **AI functions:** `scan-ingredients`, `generate-recipes` and nutrition estimates reject unverified accounts with **402 `purchase_required`** (F0.5). Non-AI features never check it.
5. **Config:** `REQUIRE_PURCHASE=false` turns enforcement off (prototype and local dev).

## Failure handling
- **Offline, or proof not available yet:** retry on the next launch and when the user first taps an AI feature. Pantry, manual entry, saved recipes and the shopping list keep working.
- **AI buttons while unverified:** they show "Verifying your purchase…" with **Retry**.
- **Proof still missing:** **Restore purchase** calls `AppTransaction.refresh()`, which may ask the user to sign in to their Apple ID. It's only called when the user taps it.

## Not in v1
Removing access after a refund needs App Store Server Notifications (DESIGN §11, backlog 9). Refunds are rare and low cost, so this is deferred.

## Acceptance criteria
- [ ] An account created with `curl` and the anon key gets 402 from `generate-recipes`.
- [ ] A TestFlight build (Sandbox proof) is verified by prod. Prod rejects Xcode proof.
- [ ] A user can't update `purchase_verified_at` through the API (RLS and column-grant test).
- [ ] Failed verification doesn't block any non-AI feature.
- [ ] Verification happens once per account, not on every request. The AI functions read the column.

> Check the StoreKit 2 `AppTransaction` fields and the App Store Server Library API against Apple's current docs when building this.
