# F1.6 Expiry rules

**Phase** 1 · **Size** S · **Prototype** yes · **Requirements** FR-4 · **Depends on** F0.3, F0.4

## Summary
One rule, in one place, that sets each pantry item's expiry date. Users can override it for a single item or for every future item of an ingredient type.

## Rule (in order of priority)
1. **Per-item override:** the user set `expires_at` themselves, so `expiry_overridden = true` and nothing recalculates it.
2. **User default for the ingredient at this location:** `user_shelf_life_overrides.days` matching (`ingredient_id`, `location`).
3. **Catalog default for the location:** `shelf_life_{fridge|freezer|pantry}_days`.
4. **Fallback** (no catalog value, or a custom item): fridge 7 days, freezer 90, pantry 30.

`expires_at = date(added_at, in the user's timezone) + days`, at the end of that local day.

## Where it runs
- A Postgres function `app.default_expiry(user_id, ingredient_id, location, added_at)`.
- A `before insert or update` trigger on `pantry_items` fills in `expires_at` when it's null or when `location` changes, but only if `expiry_overridden` is false.
- The app shows a preview with the same rule in Swift (`ExpiryCalculator`), so the add sheet can update without a network call. The server's value is final.
- The two implementations are checked by a shared table of test cases (JSON), run against both.

## User controls
- **Per item:** the date picker in the edit sheet (F1.5).
- **Per ingredient:** "Always use N days for <ingredient>" in the date picker. Also Settings → Expiry defaults, which lists the user's overrides with edit and delete.
- Changing a per-ingredient default **doesn't** change items already saved. The confirmation says so, and offers "Also update 3 existing items".

## Per-location overrides
Overrides are keyed by (user, ingredient, location), so "milk lasts 10 days" in the fridge doesn't change frozen milk. "Always use N days for <ingredient>" saves the default for the item's current location, and the Settings list shows the location on each override.

## Implementation notes (2026-11-04)
Decisions from review:
- **Timezone:** `app.user_prefs.timezone` (IANA name, default `UTC`, validated). The app saves the phone's timezone on launch when it changes.
- **Moving** recalculates from `added_at` (added date + new location's days), as above.
- **Changing `ingredient_id`** also recalculates. So does clearing `expires_at`, which is how "Also update N existing items" works (the app sets `expires_at = null` on those rows).
- **Insert** always computes the date unless `expiry_overridden`; a client-supplied date is ignored. `expiry_overridden = true` with a null date means "no expiry".
- **Whose defaults:** the item's `added_by` (falls back to the caller).
- **UI** (date picker, "Always use N days", Settings → Expiry defaults) ships with F1.5 and F1.7; F1.6 is the rule and its tests.
- Server: `app.shelf_life_days`, `app.default_expiry` (security definer, not callable by clients), trigger `set_expiry`. Swift: `ExpiryCalculator`. Shared cases: `supabase/tests/expiry_cases.json` (SQL: `expiry_test.sql`; Swift: `ExpiryCalculatorTests`).

## Acceptance criteria
- [x] The priority order holds for each case in the test table.
- [x] Moving an item from fridge to freezer extends its expiry, unless it was overridden.
- [x] A fridge override for an ingredient doesn't affect the same ingredient in the freezer.
- [x] Custom items get the fallback.
- [x] Swift and SQL results match for every test case.
