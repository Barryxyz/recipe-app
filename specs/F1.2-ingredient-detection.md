# F1.2 Ingredient detection (`scan-ingredients`)

**Phase** 1 · **Size** L · **Prototype** yes, and testing it is the main goal of the prototype · **Requirements** FR-2 · **Depends on** F0.4, F0.5, F1.1

## Summary
An Edge Function that sends the photos to `SCAN_MODEL`, gets back a structured list of ingredients, matches each one to the catalog, merges duplicates across photos and returns a draft list for review.

## API
`POST /scan-ingredients`
```jsonc
// request
{ "location": "fridge", "images": ["<base64 jpeg>", "..."] }   // 1–2 images

// response
{
  "items": [{
    "temp_id": "t1",
    "name": "eggs",                    // model's name
    "ingredient_id": 123,              // catalog match, or null
    "match": "exact|alias|fuzzy|none",
    "quantity": 6, "unit": "each",     // quantity may be null ("some")
    "confidence": 0.92,
    "low_confidence": false,
    "photo_indexes": [0]
  }]
}
```

## Model call
- **System prompt rules:**
  - List only food and drink.
  - Use generic names ("cheddar cheese", not the brand).
  - Estimate quantity in a sensible unit (each, g, ml, bunch, or the package as "each").
  - Use `null` quantity when it can't be estimated.
  - Give `confidence` from 0 to 1.
  - Don't guess at contents hidden inside opaque containers. Report a "container (unknown contents)" item only if confident, otherwise skip it.
- **Output schema:** `{ items: [{ name, quantity|null, unit|null, confidence, photo_index }] }`
- **No fallback model:** the scan model is already the strong one (D3). One retry happens only if the output fails schema parsing.

## Cost settings (2026-11-04)
- `SCAN_EFFORT` defaults to **medium** (was high). 1–2 photos per scan (F1.1).
- `./scripts/eval-scan.sh --compare` runs the eval under several model/effort settings and reports accuracy and cost per scan from `ai_usage_log`, to pick the cheapest setting that meets the targets.

## Post-processing
1. **Normalize the name:** lowercase, trim, singularize the simple cases.
2. **Match to the catalog:** exact name → alias → `search_ingredients` top result with score ≥ 0.5. Anything else is `match = none`.
3. **Merge duplicates:** items with the same `ingredient_id`, or the same normalized name when unmatched.
   - Different photos may show the same physical item, so take the **max** quantity rather than the sum.
   - Keep the lowest confidence and union `photo_indexes`.
   - If units differ, keep both items unmerged and let the user decide.
4. **Flag low confidence:** `low_confidence = confidence < 0.6 || match == 'fuzzy'`.
5. Sort by category, then name.

## Unknown items
Items with `match = none` stay unmatched in the response. They become `ingredients_private` rows only when the user saves them (F1.3). Their nutrition is estimated later, when a recipe needs it (F2.3).

This matches DESIGN §6.1a step 7: nutrition is estimated later, the same way as for manual custom items, which keeps the scan prompt and output smaller.

## Accuracy evaluation (prototype exit criterion)
- Build a test set of 15–20 real photos (cluttered and tidy fridge, freezer, pantry) with a hand-labeled list of ingredients for each.
- A script `eval/scan_eval.ts` runs the function over the set and reports:
  - **recall:** labeled items found
  - **precision:** found items that are real
  - **quantity error:** how far off the quantities are
- **Target:** recall ≥ 80% and precision ≥ 90% on tidy shelves. Record results in DESIGN §12.

## Acceptance criteria
- [ ] Returns valid JSON for 1–2 photos in under 25 s at p90.
- [ ] Duplicates across overlapping photos are merged.
- [ ] Every item has a `match` value, and low-confidence items are flagged.
- [ ] A photo with no food returns `items: []`, not an error.
- [ ] One `ai_usage_log` row is written per model call, with `kind = 'scan'`.
- [ ] The eval script runs and produces the metrics.
